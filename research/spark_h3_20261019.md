# Spark-H3 source report (checked 2026-10-19)

Sources were read from official upstream `main` (`06cf711e4b5ebd519c92a84c1771560aca99f3a0`) and the stable ComfyUI tag `comfyui-v0.1.4` (`1e12be28d62898e4bcf97b51fb6e80feb6985152`). Source was fetched read-only; no dependencies, wheels, models, CUDA, or upstream runtime were executed.

## 本專案評估與決定

Spark 值得列為後續 L4 加速候選：它沿用原生 H3 權重，能調整 producer 分塊，也已有 KJNodes 低 VRAM 接線。但目前不足以認定它比 Veda 省很多 VRAM；沒有同條件峰值記憶體比較，Fidelity 切換至稀疏步驟的尖峰也是上游已知問題。

本次不加入預設安裝。現行新工作台固定 ComfyUI 0.42／comfy-kitchen 0.2.39，與 Spark 正式包的版本範圍及專用 kitchen wheel 衝突。後續若實測，使用獨立的 ComfyUI 0.40／CUDA 13.0 環境，在 L4 先確認 wheel 與 kernel，再固定相同 H3 模型、LoRA、素材、尺寸、片長及 seed，量測 dense／Fidelity／Speed 的時間、峰值 VRAM／RAM、音訊與畫面差異。Speed 省略 dense warmup 是品質取捨，不能把加速倍率直接當成無損結果。Continuum、Spark、Ref2VA-VSA 的注意力組合須另驗，不自動疊加。

這是研究結論，沒有配置或執行上述 GPU 試驗。已交付的兩項整合入口見 [ComfyUI notebook](../notebooks/ComfyUI_Colab.ipynb) 與[操作說明](../doc/COMFYUI_WORKSPACE.md)。

## Decisive supported-version and VRAM facts

- The v0.1.4 package metadata declares `requires-comfyui = ">=0.38.0,<0.41.0"`; its installer accepts only comfy-kitchen bases `0.2.36` and `0.2.37`, mapping them to ComfyUI 0.38.x and 0.39.x/0.40.x. This is an explicit metadata/installer block for the workspace’s ComfyUI 0.42.0, before GPU testing. ([tag metadata](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/comfyui/standalone/pyproject.toml.in#L21-L24), [installer base check](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/comfyui/install.py#L15-L18), [installer error/version map](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/comfyui/install.py#L168-L177), [release tests](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/tests/test_comfyui_package.py#L907-L915))
- v0.1.4 publishes no total peak-VRAM measurements for Dense, `mode=fidelity`, or `mode=speed`. Its measured table is speed/fidelity only: Linux, ComfyUI 0.38.2, LightX2V 768p 8-step LoRA, 1344×768, 345 frames, 24 FPS, `topk_ratio=20%`, `warmup_steps=2`, dense baseline ComfyUI PyTorch SDPA. RTX 3090/SM86: Fidelity 2.42×, Speed 4.62×; RTX 4090/SM89: 2.37×/4.35×; RTX PRO 6000 Blackwell/SM120: 2.05×/3.15×. A 0.39.2 note says ratios improved slightly on RTX 3090 and PRO 6000, without publishing memory numbers. ([v0.1.3 performance record retained by v0.1.4 docs](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/docs/release_v013_intro_en.md#linux-performance), [v0.1.4 release conditions/known issue](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/docs/v014_text.md#known-issue))
- The current technical blog’s separate kernel table gives timing, not peak VRAM: VBench prompts, 20-point MiniMax-H3 schedule/19 denoiser steps, 1344×768, 240 frames at 24 FPS, paired prompts/seeds; Dense DiT 583.3 s, Spark 10% 337.4 s (1.73×), Spark 20% 371.1 s (1.57×), Spark 30% 404.1 s (1.44×). The integration protocol states 1344×768/240 frames/24 FPS and a single RTX PRO 6000 Blackwell Server Edition 96 GB for its few-step/FastH3 comparisons; DiT timing excludes VAE and other end-to-end work. The same section says FastH3 VSA variants exceed 96 GB when fully resident and were layerwise-offloaded; that is a VSA memory note, not a Spark Dense/Fidelity/Speed peak measurement. ([benchmark setup/table](https://github.com/zechengtang/Spark-H3/blob/06cf711e4b5ebd519c92a84c1771560aca99f3a0/docs/blogs/spark-attn/README.md#benchmark-results), [integration conditions](https://github.com/zechengtang/Spark-H3/blob/06cf711e4b5ebd519c92a84c1771560aca99f3a0/docs/blogs/spark-attn/README.md#spark-integration))
- There is no direct measured Spark-versus-Veda A/B table in the checked sources. The blog names Veda in a conceptual related-work discussion and states Veda learns block scores; it does not report Veda VRAM or a matched Spark/Veda run. Spark has no separate attention predictor artifact; the ComfyUI package says H3 model weights are not included, and workflows reuse native Comfy-Org MiniMax-H3 files plus optional separately downloaded LoRAs. Do not treat Veda’s separate 275 MB predictor as Spark runtime memory. ([related-work discussion](https://github.com/zechengtang/Spark-H3/blob/06cf711e4b5ebd519c92a84c1771560aca99f3a0/docs/blogs/spark-attn/README.md#discussion), [model/workflow requirements](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/comfyui/README.md#models-and-workflows), [package scope](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/README.md#comfyui-installation))
- The only explicit VRAM guidance is qualitative: `producer_chunk` defaults to 16,384 tokens and smaller positive multiples of 64 may lower temporary producer memory at speed cost; v0.1.4 records an unresolved high-VRAM spike when Fidelity switches from dense warmup to sparse steps and suggests lowering `producer_chunk` or using Speed. KJNodes smaller chunks are also described as generally reducing VRAM with overhead. No peak value is supplied. ([v0.1.4 notes](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/docs/v014_text.md#known-issue), [node parameters](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/docs/comfyui_spark_node_parameters.md#所有输入))

## Architecture, CUDA, node, and model boundaries

- Official v0.1.4 ComfyUI packages target Linux/Windows x86_64, Python 3.12+ in the install guide, PyTorch CUDA 13.0, CUDA BF16, and SM86/SM89/SM120. Release wheels are architecture/OS-specific; CUDA 12.8 is outside the release. The installer supports only `(8,6)→sm86`, `(8,9)→sm89`, `(12,0)→sm120`; T4/SM75 is rejected. L4 is SM89 at the capability level, but the release docs name GeForce RTX 40 for SM89 and provide no L4 validation. A100/SM80 is not in the standalone ComfyUI package mapping, although the separate Diffusers Spark code documents an SM80 fused path; that does not establish ComfyUI-node support. ([v0.1.4 support](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/comfyui/INSTALL.zh-CN.md#支持范围), [installer architecture/CUDA map](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/comfyui/install.py#L15-L31), [Diffusers architecture scope](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/h3_sparse_attention/README.md#requirements))
- The v0.1.4 node IDs are `MiniMaxH3SparkAttentionSM86`, `MiniMaxH3SparkAttentionSM89`, and `MiniMaxH3SparkAttentionSM120`; display names are `MiniMax H3 Spark Attention (SM86/SM89/SM120)`. The Spark node requires `model` (`MODEL`), `mode`, `steps`, `warmup_mode`, `warmup_ratio`, `warmup_steps`, `topk_mode`, `topk_ratio`, `topk_blocks`, `dense_layers`, `min_tokens`, and `strict`; optional inputs are `dense_backend`, `tail_granularity`, `reblock_layout`, `sparse_scope`, and `producer_chunk`; it returns one `MODEL`. The patch requires native `MiniMaxH3Model` and applies ComfyUI block replacements. ([node schema](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/comfyui_nodes.py#L981-L1075), [mapping/compatibility](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/comfyui_nodes.py#L1102-L1169), [mappings](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/comfyui_nodes.py#L1525-L1541))
- The documented attention order is `model loader → MiniMax H3 Low VRAM Attention → MiniMax H3 Chunk FeedForward → Spark Attention → BasicGuider/sampler`; both KJNodes patches are separate dependencies. The guide says apply only one attention patch to a model. The checked Spark and Continuum trees contain no explicit `Continuum`/`H3 Continuum` interoperability statement, so that combination is unverified from primary source. ([ComfyUI guide](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/comfyui/README.md#kjnodes-low-vram-patches), [patch order/source](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/comfyui_nodes.py#L1111-L1169))
- Spark reuses native Comfy-Org MiniMax-H3 diffusion/text/VAE files; examples include native 20-step no-LoRA, LightX2V 8-step, Larryvrh 8-step, DMAD 4-step, and LBH two-pass workflows. Additional LoRAs/upscaler/third-party nodes are separate. No Spark predictor or new H3 checkpoint is declared. ([models/workflows](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/comfyui/README.md#models-and-workflows))

## Low-VRAM and roadmap facts

- v0.1.4’s `producer_chunk` is a Python-side chunk-size control, default 16,384, range 64–262,144, step 64; lowering it may reduce temporary memory without rebuilding the wheel. KJNodes Low VRAM Attention must precede Spark and Chunk FeedForward is orthogonal. ([parameter reference](https://github.com/zechengtang/Spark-H3/blob/1e12be28d62898e4bcf97b51fb6e80feb6985152/docs/comfyui_spark_node_parameters.md#所有输入))
- Current roadmap says v0.1.5 will reduce peak VRAM through fewer temporary allocations and better memory reuse, and reduce sustained GPU power while retaining quality/speed gains. This is planned, not a v0.1.4 measurement or release. ([roadmap](https://github.com/zechengtang/Spark-H3/blob/06cf711e4b5ebd519c92a84c1771560aca99f3a0/README.md#project-status--roadmap))

## Search boundary

The official source/docs/release assets were inspected with static text/AST/JSON reads only. The repository’s top-level `COMFYUI.md` is stale relative to the v0.1.4 guide/installer: it still lists only ComfyUI 0.38/0.39 and SM89/SM120, while the v0.1.4 metadata, release guide, and installer add 0.40 and SM86. No Spark Dense/Fidelity/Speed peak-VRAM number, matched Veda A/B measurement, L4 run, A100 ComfyUI-node run, or T4 run was found in the checked Spark-H3 sources. The explicit blocker for ComfyUI 0.42.0 is the package range `<0.41.0`; bypassing it would be outside the published support contract.
