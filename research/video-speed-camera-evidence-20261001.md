# Video speed / camera evidence (checked 2026-10-01)

This is a bounded primary-source lookup for lower-resolution Wan generation followed by temporal video super-resolution (VSR), and for explicit camera control. It does not test a GPU, compare quality, or infer a speedup. GitHub API values below are snapshots taken on 2026-10-01; star/contributor counts are not evidence of organic growth or bus factor.

## Search audit

The two requested discovery queries were exactly: `site:github.com video super resolution camera control Wan Colab` and `site:github.com awesome-video-super-resolution`.

## Official Wan2.2 boundary

- [Wan-Video/Wan2.2 README, I2V section](https://github.com/Wan-Video/Wan2.2/blob/main/README.md#run-image-to-video-generation) says `Wan2.2-I2V-A14B` supports 480P and 720P; the example is `--size 1280*720`, requires at least 80 GB VRAM, and says I2V `size` is the generated-video area while preserving the input-image aspect ratio (README lines 191-204 at the checked revision).
- [Wan config](https://github.com/Wan-Video/Wan2.2/blob/main/wan/configs/__init__.py) enumerates I2V-A14B sizes `720*1280`, `1280*720`, `480*832`, `832*480` (lines 21-46). `640*352` and `320*176` are not documented official I2V sizes.
- The same README documents only the separate TI2V-5B as 720P@24 FPS and under 9 minutes for a 5-second 720P video on one consumer GPU; this is not an A14B benchmark ([README high-definition section](https://github.com/Wan-Video/Wan2.2/blob/main/README.md#2-efficient-high-definition-hybrid-ti2v), lines 466-467).
- Wan API snapshot: [`GET /repos/Wan-Video/Wan2.2`](https://api.github.com/repos/Wan-Video/Wan2.2): Apache-2.0, main, 17,677 stars; latest main commit [`1ea34ff48f87168174e12956e200b1d908b1c5ff`](https://github.com/Wan-Video/Wan2.2/commit/1ea34ff48f87168174e12956e200b1d908b1c5ff), 2026-09-21. Latest PRs were #398 (open, 2026-09-28), #396 (open, 2026-09-27), #393 (open, 2026-09-23); `/releases/latest` returned 404.

## Candidate evidence

### SeedVR2 (official repo: ByteDance-Seed/SeedVR)

- API snapshot: [`GET /repos/ByteDance-Seed/SeedVR`](https://api.github.com/repos/ByteDance-Seed/SeedVR): Apache-2.0, main, 1,380 stars, not archived; latest main commit [`e4de8c24441a67e1b7df56abea10645059bb1185`](https://github.com/ByteDance-Seed/SeedVR/commit/e4de8c24441a67e1b7df56abea10645059bb1185), 2026-01-27. `/releases/latest` 404; latest visible PR #33 was closed 2025-09-10; contributor endpoint returned IceClear (7) and numz (2). This is a maintenance snapshot only.
- [Official README](https://github.com/ByteDance-Seed/SeedVR/blob/main/readme.md#-inference), lines 167-176, gives `torchrun ... projects/inference_seedvr2_3b.py --video_path INPUT_FOLDER --res_h OUTPUT_HEIGHT --res_w OUTPUT_WIDTH --sp_size NUM_SP`. It states one H100-80G handles `100x720x1280` video and four H100-80G support 1080p/2K (`sp_size=4`). No inference FPS is documented.
- [Official inference script](https://github.com/ByteDance-Seed/SeedVR/blob/main/projects/inference_seedvr2_3b.py#L229-L266) accepts image/video inputs, resizes to target pixel area (`res_h*res_w`, upsample allowed because “model only trained for high res”), crops to 16-pixel divisibility, and feeds a frame sequence. This is temporal video restoration, not independent framewise image SR; that distinction is an interface-based inference, not a measured guarantee.
- [Official limitations](https://github.com/ByteDance-Seed/SeedVR/blob/main/readme.md#-notice), lines 118-119, warn about heavy degradation/large motion and over-generated details/oversharpening on lightly degraded 720p AIGC video, especially 480p. No explicit face-identity guarantee was found.
- Code `LICENSE` and [SeedVR2-3B model-card front matter](https://huggingface.co/ByteDance-Seed/SeedVR2-3B/blob/main/README.md) independently state Apache-2.0. No Wan-specific adapter is documented; it is a generic video post-processor and can consume a Wan output file if resources permit.

### FlashVSR (official repo: OpenImagingLab/FlashVSR)

- API snapshot: [`GET /repos/OpenImagingLab/FlashVSR`](https://api.github.com/repos/OpenImagingLab/FlashVSR): Apache-2.0, main, 1,880 stars, not archived; latest main commit [`cf910c61a60733e610e9c6e8b607f80c3a6c202b`](https://github.com/OpenImagingLab/FlashVSR/commit/cf910c61a60733e610e9c6e8b607f80c3a6c202b), 2026-09-01. `/releases/latest` 404; latest visible PR #22 is open (2026-07-16); contributor endpoint returned zhuang2002 (41). This is a maintenance snapshot only.
- [README abstract](https://github.com/OpenImagingLab/FlashVSR/blob/main/README.md#-abstract), lines 19-21, describes one-step streaming VSR and reports about 17 FPS at 768x1408 on one A100; the number is not a Colab or Wan benchmark. [Getting started](https://github.com/OpenImagingLab/FlashVSR/blob/main/README.md#-getting-started), lines 85-90, says it is primarily designed/optimized for 4x and strongly recommends 4x. The original README gives no VRAM minimum; [NVIDIA FlashDreams docs](https://github.com/NVIDIA/flashdreams/blob/main/docs/source/models/flashvsr.rst) separately state ~24 GB minimum for that integration.
- [Pinned v1.1 full script](https://github.com/OpenImagingLab/FlashVSR/blob/cf910c61a60733e610e9c6e8b607f80c3a6c202b/examples/WanVSR/infer_flashvsr_v1.1_full.py#L48-L93) accepts MP4/MOV/AVI/MKV or an image folder, computes `input * scale`, rounds each target dimension down to a 128-pixel multiple, then center-crops the bicubic-upscaled frame to that target. At the checked revision, `scale=4` is set in `main` (lines 189-199). Therefore 320x176 -> scaled 1280x704 -> output 1280x640 (height 704 floored to 5*128); 640x352 -> scaled/output 2560x1408 (1408 is 11*128). [Video preparation](https://github.com/OpenImagingLab/FlashVSR/blob/cf910c61a60733e610e9c6e8b607f80c3a6c202b/examples/WanVSR/infer_flashvsr_v1.1_full.py#L125-L156) appends four copies of the final frame, sets `F = largest_8n1_leq(N+4)` (where `largest_8n1_leq` is lines 30-31), and truncates the index list to `F`; the script prints `F-4` as a nominal unpadded count but has no post-inference trim. It calls the pipeline with `num_frames=F` and saves the returned frames (lines 204-215). For an 81-frame input, `N+4=85`, `F=81`, so the wrapper passes 81 frames for either spatial case. This does not prove 81 returned output frames: the [pinned streaming pipeline](https://github.com/OpenImagingLab/FlashVSR/blob/cf910c61a60733e610e9c6e8b607f80c3a6c202b/diffsynth/pipelines/flashvsr_full.py#L357-L449) constructs chunks, decodes their latents, and returns the decoded tensor; the actual returned frame count, temporal coverage and PTS require separate verification. In general, `F=8*floor((N+3)/8)+1`; input frames may be truncated when `F < N`. A 2x path is not documented by the official scripts and would require changing `scale`; e.g. at scale=2, 640x352 would become 1280x640, not 1280x704.

| Input | x4 resize before crop | Script target/output | Center crop | `F` for 81 input frames |
|---|---:|---:|---:|---:|
| 320x176 | 1280x704 | 1280x640 | top=32, left=0 | 81 |
| 640x352 | 2560x1408 | 2560x1408 | top=0, left=0 | 81 |
- [GPU/backend note](https://github.com/OpenImagingLab/FlashVSR/blob/main/README.md#-install-block-sparse-attention-required), lines 115-123, reports ideal acceleration on A100/A800, correct but limited acceleration on H200, and unknown compatibility/performance on RTX 40/50 and H800. The README warns third-party wrappers that omit LCSA can visibly degrade high-resolution quality. Code `LICENSE` and [v1.1 model-card front matter](https://huggingface.co/JunhaoZhuang/FlashVSR-v1.1/blob/main/README.md) independently state Apache-2.0. No explicit face-identity guarantee was found.

### Wan2.2-Fun camera (official code: aigc-apps/VideoX-Fun)

- API snapshot: [`GET /repos/aigc-apps/VideoX-Fun`](https://api.github.com/repos/aigc-apps/VideoX-Fun): Apache-2.0, main, 2,275 stars, not archived; latest main commit [`4b7b6402a1e0f0406bd6801fb66c0a00bd922621`](https://github.com/aigc-apps/VideoX-Fun/commit/4b7b6402a1e0f0406bd6801fb66c0a00bd922621), 2026-09-29. `/releases/latest` 404; latest visible PR #521 closed 2026-09-29; contributor endpoint returned bubbliiiing (148), hkunzhe (15), Tianhao-Qi (4). This is a maintenance snapshot only.
- This is an actual camera input interface, not prompt-only camera wording. [Wan2.2 camera script](https://github.com/aigc-apps/VideoX-Fun/blob/main/examples/wan2.2_fun/predict_v2v_control_camera.py#L85-L120) selects `Wan2.2-Fun-A14B-Control-Camera`, reads `control_camera_txt`, and defaults to `sample_size=[480,832]`, 81 frames, 16 FPS. [Pipeline call](https://github.com/aigc-apps/VideoX-Fun/blob/main/examples/wan2.2_fun/predict_v2v_control_camera.py#L302-L332) parses that file into `control_camera_video` and passes it to `Wan2_2FunControlPipeline`; [pose parser](https://github.com/aigc-apps/VideoX-Fun/blob/main/videox_fun/data/utils.py#L337-L374) consumes per-frame intrinsics plus 3x4 poses and constructs Plücker embeddings.
- [Camera utility](https://github.com/aigc-apps/VideoX-Fun/blob/main/comfyui/camera_utils.py#L7-L21) exposes Static, Pan Up/Down/Left/Right, Zoom In/Out, and ACW/CW. [Comfy docs](https://github.com/Comfy-Org/docs/blob/main/tutorials/video/wan/wan2-2-fun-camera.mdx#wan2-2-fun-camera-control-video-generation-workflow-example), lines 9-18 and 139-143, document the same camera modes plus speed/length controls; the 640x640, 81-frame RTX4090D-24GB example reports fp8 536s first / 513s second at 84% VRAM, or 4-step LoRA 108s / 71s at 89% VRAM, with a warning that the LoRA may reduce dynamics.
- [Wan2.2-Fun camera model card](https://huggingface.co/alibaba-pai/Wan2.2-Fun-A14B-Control-Camera/blob/main/README.md) declares `base_model: Wan-AI/Wan2.2-I2V-A14B`, multi-resolution 512/768/1024, 81 frames at 16 FPS, and Apache-2.0. The code and weight-card licenses match. This is a Wan2.2-Fun control checkpoint, not a drop-in camera adapter for the stock Wan2.2-I2V-A14B checkpoint. 320x176 and 640x352 generation support is undocumented.
- VideoX-Fun README documents CPU-offload, float8 quantization, and sequential offload; sequential saves more GPU memory but is slower. No Colab-specific timing was found.

### CamI2V (camera comparator, not Wan-compatible)

- API snapshot: [`GET /repos/ZGCTroy/CamI2V`](https://api.github.com/repos/ZGCTroy/CamI2V): MIT, main, 171 stars, not archived; latest main commit [`c5d7b2fcdeb89a1ce9a0ef376909d9539b95639f`](https://github.com/ZGCTroy/CamI2V/commit/c5d7b2fcdeb89a1ce9a0ef376909d9539b95639f), 2025-09-29 (just outside the 12-month lookback at this check date). `/releases/latest` and pull list were empty; contributor endpoint returned MuteApo (20) and ZGCTroy (5).
- [Demo](https://github.com/ZGCTroy/CamI2V/blob/main/demo/cami2v_test.py#L156-L221) reads named pose files containing per-frame camera matrices, converts them to relative poses, and injects them into the model; the README lists 256x256 and 512x320 checkpoints and reports 11.67 GiB / 10.3 s on RTX 3090 for CamI2V under its 256x256 benchmark conditions ([README performance](https://github.com/ZGCTroy/CamI2V/blob/main/README.md#performance), lines 62-80). Code `LICENSE` and [HF model-card front matter](https://huggingface.co/MuteApo/CamI2V/blob/main/README.md) independently state MIT.
- The implementation is DynamiCrafter-based (`CameraControl/base/base.py`), not Wan2.2, and no official Wan adapter is documented; treat as a camera-control reference only. No face-identity guarantee was found.

## CameraCtrl II search boundary

[CameraCtrl II’s official CVF page](https://openaccess.thecvf.com/content/ICCV2025/html/He_CameraCtrl_II_Dynamic_Scene_Exploration_via_Camera-controlled_Video_Diffusion_Models_ICCV_2025_paper.html) explicitly describes iterative user-specified camera trajectories and says code will be released, but the bounded GitHub search found no official repository to API-audit. ## Uncertainty / applicability

- VSR model temporal behavior is supported by their video-sequence interfaces and model descriptions; no candidate was run here, so temporal consistency, hallucination rate, and face identity on the child/sedan clip remain unverified.
- Wan2.2 official A14B does not document 320x176 or 640x352 generation. Those are therefore test hypotheses, not supported settings. At the pinned FlashVSR revision, 4x processing maps 320x176 to 1280x640 after the required crop, while 640x352 maps to 2560x1408; neither is a direct 1280x704 output. A 2x path needs validation or code changes.
- Dependency licenses/CVEs were not audited. The candidate code/weight license checks above do not grant rights for third-party dependencies or base models beyond their own published terms.
